## Feature release — HTTP transport hardening, profile-value writes, and activity recipients

This release bundles three independent improvements since v0.4.1. **Default stdio
deployments keep working unchanged**; the behaviour changes are confined to the
networked HTTP/SSE transport (opt-in) and to two tools whose writes were previously
unreliable.

## HTTP transport config hardening and a health route (#16)

Follow-ups from the Streamable HTTP work. None of these affect the default stdio
setup, but each turns an operator typo on a networked deployment from silent
misbehaviour into a clear, early failure.

- **Strict boolean env parsing.** `ACCELO_MCP_STATELESS`, `ACCELO_MCP_JSON_RESPONSE`
  and the other boolean variables now accept a fixed vocabulary
  (`1/true/yes/on` vs `0/false/no/off`, case-insensitive) and raise a startup error
  naming the variable on anything else. Previously a typo such as
  `ACCELO_MCP_STATELESS=ture` silently ran stateful.
- **argparse CLI.** Transport selection moved to `argparse` with a mutually-exclusive
  group (`--http`/`--streamable-http`, `--sse`; stdio is the default). Unknown or
  conflicting flags now exit non-zero with usage, and `--help` is available.
  `accelo-mcp --htpp` no longer silently starts stdio.
- **`ACCELO_MCP_PATH` validation.** A path without a leading slash is now rejected at
  startup rather than passed unchecked into routing.
- **Startup security log.** The HTTP/SSE startup line now reports the effective
  DNS-rebinding protection state and the Host/Origin allow-lists, so a
  `421 Misdirected Request` behind a proxy is diagnosable.
- **`GET /healthz`.** A cheap liveness route (HTTP 200) for load balancers and
  container platforms, exempt from the Host allow-list so it can be probed by
  instance IP.

**Behaviour change for networked operators:** a blank/misspelled boolean env var, a
path without a leading slash, and unknown/conflicting CLI flags now fail at startup
instead of running in a surprising mode. The README and `.env.example` document the
accepted values and which variables apply to `--sse` vs `--http`.

## Profile-value writes now persist and are verified (#22)

`accelo_set_profile_value` returned `ok` but silently failed to persist the value for
hyperlink (and other custom) profile fields — a false-positive write.

- The write now uses Accelo's dedicated profile-value endpoint
  (`POST /{object}/{id}/profiles/fields/{field_id}`) instead of the create-company
  shortcut that silently ignored the value.
- The request body is shaped by the field's type (`value` for hyperlink/text/etc.,
  `value_int` for integer, `value_date` for date, `value_id` + `value_type` for
  lookup). Lookup fields now require `value_type`.
- After writing, the value is read back and compared; a mismatch or missing row
  returns an error (`verify_failed`) instead of a false success, so the tool can
  never report a silent no-op as `ok` again.
- Non-integer values for integer fields are rejected up front (`invalid_value`), and
  the field-type lookup is paginated so fields beyond the first page resolve.

## create_activity can address recipients (#23)

`accelo_create_activity` could not set a recipient role, so an email or meeting
activity could not be addressed **to** a named staff member or contact — the party
either became the author or landed as `bcc`.

- New `to`, `cc` and `bcc` parameters, each an object keyed by `staff`,
  `affiliation` or `emails` (e.g. `to={"staff": [10]}`,
  `cc={"affiliation": [13, 14]}`, `bcc={"emails": ["x@y.com"]}`).
- The owner remains the sender (`from`); a recipient named under `to` is now
  addressed as `to` rather than silently demoted to `bcc`.
- When recipients are supplied the request is sent as JSON (required for these
  interactions); with no recipients the existing form-encoded path is unchanged, so
  existing callers are unaffected.
